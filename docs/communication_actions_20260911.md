# 笔记与邮件离线接口：合成验证阶段

所有者确认 AIB 少量试点之后的下一阶段。本阶段根据两个排除原因补充接口，仅使用合成 fixture，没有新增真实来源观测或改写历史试点文件。

## 实现

新增 `src/intentfence/communication_actions.py`、`configs/communication_actions_v1.yaml` 和 `tests/test_communication_actions.py`。新模块使用独立的严格 Pydantic 契约；原 `offline_actions.py`、AIB 准备记录和 run_v1 保持原有字节，历史策略哈希仍可核验。

| 接口 | 参数 | 边界 |
|---|---|---|
| memory.note_save_proposal | title、body | 标题不变成路径；不创建文件或调用笔记服务 |
| memory.email_send_proposal | to、cc、bcc、body | 三种收件人分别为列表，空 CC/BCC 必须显式表示；不发送邮件 |

每个正文、标题和收件人都提供原消息的字符范围候选，以及当前 user 请求中的授权依据。多轮“那个摘要”等指代由准备者显式绑定此前内容；代码不自动从自然语言推断指代。没有候选则澄清；多个候选则澄清，不以“最后一个”或任意排序决定正文。源内容可来自历史 assistant、user 或工具返回；授权必须绑定最新 user，不能用旧用户请求或工具返回冒充新的授权。

goal_bounded 对每个字段及每个 To/CC/BCC 收件人检查是否有当前授权依据。缺少任一项时返回澄清，不偷偷删去某个收件人后当作完成。content_following 可以记录准备者指定的低信任建议，包括未获授权的额外 BCC，用作离线对照；正文缺失和歧义仍然不会自动补造。该策略名不产生 Risk 或 Alignment 标签。

收件人参数采用有限的单地址字面值检查，拒绝换行、拼接地址、显示名/尖括号等未支持的形式。多个收件人必须分别列出并保留各自证据。这不是完整 RFC 邮箱验证或地址可达性检查。

记录包含输入、配置、实现及共享契约代码哈希、逐字段来源和授权位置、选择分支。没有笔记库、邮箱或文件资源写入；全部是内存中的提案。`executed`、`external_side_effects`、`human_verified`、`training_ready` 均为 false，Risk/Alignment/split 为空。

## 验证与限制

24项新 fixture 测试覆盖：历史摘要引用、title 与 path 的区分、To/CC/BCC 独立来源、授权 BCC 保留、未授权收件人澄清、同工具不同 BCC 提案、多收件人、缺正文、歧义指代、旧/低信任授权拒绝、未来消息边界、字段缺失、非法地址片段、输入修改重验证和无外部调用。完整测试、构建及旧试点核验结果见进度计划。

当前授权检查证明引用位置属于当前 user，不能证明 AI 对该句自然语言的解释必然正确。准备者仍可能错误绑定对象或把未被授权的动作解释为授权；需要后续逐条语义审核。多个候选如被准备者错误缩成一个，框架也无法自行发现遗漏。因此不得称为已经解决自然语言指代或权限判断，更不能据 fixture 成功宣称模型收益。

## 下一阶段建议

使用专用笔记契约重新适配 AIB-00139：核对用户对前文摘要的指代，只使用动作前的标题和正文证据，不借用后续示范 tool_call 的参数。AIB-00159 仍缺 Q3 摘要正文，新增 BCC 字段不能填补这个缺口；可形成缺字段澄清记录并继续排除发送候选。保持隔离、不赋训练标签、不划 split、不训练。该真实来源适配阶段待所有者确认。
